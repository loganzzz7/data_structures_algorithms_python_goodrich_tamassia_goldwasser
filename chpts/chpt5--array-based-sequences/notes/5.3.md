# 5.3 Dynamic Arrays and Amortization
- When creating a low-level array in a computer system, the precise size of that array must be explicitly declared in order for the system to properly allocate a consecutive piece of memory for its storage.
    - This is because neighbouring memory may be used to store other things and if not given an explicit size then problem arises when trying to add additional elts to the array
- In the context of representing a Python `tuple` or `str` instance, this constraint is not an issue since instances of those classes are immutable so their size can be fixed when instantiating
- Python's `list` class has a particular length when constructed but the class allows us to add elts to the list with no apparent limit on the overall capacity of the list -> this is achieved via utilizing a **dynamic array**
    - A list instance maintains an underlying array that often has greater capacity than the curr length of the list 
        - i.e. if the user requests a list w five elts the system may have reserved an underlying array capable fo storing eight object references (rather than only 5). This extra capacity makes it easy to append a new elt to the list by using the next available cell of the array
    - If a user continues to append until all reserved are exhausted -> then class requests a new, larger array from the system and inits the new array so that its prefix matches that of the existing smaller array. After this new arr is created, the old one is reclaimed and the mem is freed

## 5.3.1 Implementing a Dynamic Array
- Although the Python `list` class provides a highly optimized implementation of dynamic arrays -> following still explores how such a class may be implemented:
    - The key is to provide means to grow the array `A` taht stores the elts of a list--cannot actually grow since the capacity is fixed
    - So if an elt is appended to a list at a time when the underlying array is full, do the following:
        1. Allocate a new array $B$ with larger capacity
        2. Set $B[i] = A[i]$ for $i = 0, ..., n-1$ where $n$ is the curr num of items (in filled up array $A$)
        3. Set $A = B$, now $A$ is the new larger cap array $B$
        4. Insert the new elt in the new array! and finish the insertion process
    - To determine how large of a new array to create -> a commonly used rule is for the new array to have twice the capacity of the existing array
        - `Dynamic Array` implementation:
        ```Python
        import ctypes

        class DynamicArray:
            """A dynamic array class akin to a simplified Python list"""
            def __init__(self):
                """Create an empty array"""
                self._n = 0 # count actual elts
                self._capacity = 1 # default array capacity
                self._A = self._make_array(self._capacity) # make a low-level array -> w ctypes to deal w low-level
            
            def __len__(self):
                """Return the num of elts in the array"""
                return self._n

            def __getitem__(self, k):
                """Return elt at idx k"""
                # check if idx in range
                if not 0 <= k < self._n:
                    raise IndexError("index oob error")
                return self._A[k]
            
            def append(self, obj):
                """Append an elt to the array"""
                if self._n == self._capacity:
                    # not enough room -> double cap on resize
                    self._resize(self._capacity * 2)
                self._A[self._n] = obj
                self._n += 1
            
            # non-public func! `_func`
            def _resize(self, c):
                """Resize internal array to capacity c"""
                B = self._make_array(c)
                for k in range(self._n):
                    B[k] = self._A[k]
                self._A = B
                self._capacity = c
            
            # non-public func
            def _make_array(self, c):
                """Return new array w cap c"""
                return (c * ctypes.py_object)()
        ```

## 5.3.2 Amortized Analysis of Dynamic Arrays
- Analysis of the running time of operations on dynamic arrays using big-Omega
    - Since we double the capacity at every resize which means that $n$ new elts can be appended before needing to resize again (so there are many cheap appends before an expensive resize) -> the $\Omega(n)$ time becomes amortized to $O(n)$!
        - To perform an **amortized analysis**, use an accounting technique where we view the computer as a coin-operated appliance that requires payment of one dollar for a constant amount of computing time. When an op is executed, we should have enough dollars available in our curr bank to pay for that op's running time. Therefore, the total amt of dollars spent for any computation == proportional to the total time spent on that computation -> can overcharge some operations in order o save up dollars to pay for others.
            - **Geometric Increase in Capacity** can also be used--i.e. increase the array by only 25% of the curr size in each resize, this saves space and can still be proven to have $O(1)$ amortized bound
            - **Arithmetic Progression**. This may be tried to minimize space wasted, however, the overall cost ends up being $\Omega(n^2)$--quadratic
- **Memory Usage and Shrinking an Array**:
    - Another consequence of the rult of a geometric increase in capacity when appending to a dynamic array is that the final array size is guaranteed to be proportional to the overall num of elts--the data structure uses $O(n)$ space
        - If a container--i.e. `list`--provides operations that cause the removal of one or more elts, greater care must be taken to ensure that a dynamic array guarantees $O(n)$ memory usage -> the risk is that repeated insertions may cause the underlying array to grow arbitrarily large and so there no longer exists proportional relationship between the actual num of elts and teh array cap after many elts are removed
            - Therefore, a good implementaion of such a data structure will shrink the underlying array on occasion while maintaining the $O(1)$ amortized bound on individual operations
                - **A strategy**: shrink the array capacity by half whenever the num of actual elts falls below a quarter of the capacity -> guaranteeing that the array cap is at most four times the num of elts.
